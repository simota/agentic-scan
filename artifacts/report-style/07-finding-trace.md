# 07 Finding Trace

## Concept

Arrange findings in recorded order. Follow the list using each finding's position on the horizontal axis and its verification verdict at the end of the row. Read the selected finding's details in this order: affected file, evidence, and fix direction.

## Why It Fits agentic-scan

Each trace row uses the sample finding ID, location, severity, and verification verdict. The false positive F-004 stays in its original position. Use the same monospace typeface and severity colors as the LP. The axis represents JSON array order, and the report states that start time and duration were unrecorded.

## Adapting It to Other Skills

- **ux-scan** takes the starting point for the recorded order from the screen or user flow, then shows the affected screen, supporting observations, and proposed improvements in sequence.
- **bug-scan** links the historical origin to locations still present in the code in the finding details. If the history has timestamps, label the axis with what the commit timestamps or recorded times represent.

## Integration and Effort

**Medium to large, about 2–3 person-days** (initial integration and verification in security-scan). Replace the list generated by `DASHBOARD` in `render.py` with trace rows, preserving the original order and connecting the existing filters, detail expansion, and anchors. Add a compact trace to the PDF's `render_assessment_html()` and link to it from the body. In `dashboard.css`, define the axis and verdict column, a vertical view for narrow screens, and a compact print view. The order can be derived from existing data, so the data format can stay as it is.

## Limitations

The horizontal axis shows only order, so with many findings the points cluster and become hard to compare. On narrow screens, the horizontal axis collapses into a vertical list, leaving finding order and verdicts as the cues for following the trace. Use cases that need timestamped measurements require an additional data source.
